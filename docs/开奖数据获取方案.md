## 0. TL;DR（先看这里）

**实测后结论与 v1 版相反：iOS 端可以直连官网，而且应该直连。**

| v1 版判断（已推翻） | v2 实测结论 |
|---|---|
| ❌「官网反爬严格，iOS 直连极不稳定」 | ✅ 福彩官网**对所有 UA 全开**，裸请求即 200，延迟 **55~117 ms** |
| ❌「体彩官网需伪造 UA + Referer」 | ✅ 只在「UA 含 `Mozilla` **且**缺 Referer」时封 567；iOS 默认 UA（`CFNetwork/...`）**不含 Mozilla，直接 200**，延迟 83~356 ms |
| ❌「推荐走 GitHub CDN 镜像」 | ⚠️ 镜像实测 **2~25 秒**，`raw.githubusercontent` 多次 25s 超时。**比官网慢 50~300 倍** |

### 推荐组合

```
主力：官网 API 直连（快、字段全、含奖池/奖级/兑奖截止日）
      ├── 双色球  cwl.gov.cn    一次请求拿最近 2078 期（含奖池+6档奖级）
      └── 大乐透  sporttery.cn  翻 30 页拿全部 2938 期（含奖池+9档奖级+兑奖期+PDF）

补充：GitHub 镜像（只用于补福彩官网拿不到的 2003~2012 老数据，或官网挂掉时兜底）
```

### 三个关键数字

- **福彩官网只保留最近 2078 期**（`2013001 ~ 2026120`）。`issueCount` 传多大都封顶 2078，更早的 2003~2012 年数据官网拿不到，只能用镜像。
- **体彩 `pageSize` 硬上限 100**。全部 2938 期需翻 30 页，实测 23.2 秒抓完。
- **体彩 `prizeLevelList` 有 9 项 = 7 个奖级 + 2 个追加奖级**。你的 `PrizeChecker` 只实现了 6 级且映射有误，见 [§4](#4-官方奖级规则实测反推确认)。

### 数据可信度已交叉验证

| 比对 | 样本 | 结果 |
|---|---|---|
| `yangxb919` 镜像 vs 福彩官网 | 双色球最近 30 期 | **0 处不一致** ✅ |
| `yangxb919` 镜像 vs 体彩官网 | 大乐透最近 30 期 | **0 处不一致** ✅ |
| `yangxb919` 镜像 vs 体彩官网全量 | 大乐透全部 2938 期 | **0 处不一致** ✅ |

## 3. 数据源详解

### 3.1 福彩官网 API（双色球）✅ 实测通过

```
GET https://www.cwl.gov.cn/cwl_admin/front/cwlkj/search/kjxx/findDrawNotice?name=ssq&issueCount=30
```

**实测结论：无任何反爬门槛。** 用 8 种 UA 组合测试，**全部返回 200**：

| User-Agent | Referer | 结果 |
|---|---|---|
| （不发任何头） | — | ✅ 200 |
| `LotteryAssistant/1.0 CFNetwork/1560.4.6 Darwin/24.0.0`（**iOS URLSession 真实 UA**） | — | ✅ 200 |
| 同上 | `https://static.sporttery.cn/` | ✅ 200 |
| `Mozilla/5.0` | — | ✅ 200 |
| 完整 Chrome UA | — | ✅ 200 |
| `curl/8.7.1` | — | ✅ 200 |
| 空字符串 | — | ✅ 200 |

- 落地 IP `60.163.129.136`，`Server: nginx`，`Content-Type: text/json;charset=UTF-8`
- `Cache-Control: no-cache, no-store, max-age=0, must-revalidate` → **CDN/URLCache 缓存无效，每次都是全量回源**
- 延迟 **55~117 ms**，2078 期全量 1.77 MB 用时 **0.85 s**
- `http://` 明文访问 → `302` 跳 `https://`，所以直接用 https 即可，**无需改 ATS**
- 注意：官网**首页** `https://www.cwl.gov.cn/kjxx/ssq/` 反而返回 **403**，但 API 路径完全开放。别被首页误导以为要拿 Cookie —— **实测不需要 Cookie**。

#### 请求参数

| 参数 | 说明 | 排序 | `Tflag` |
|---|---|---|---|
| `name` | `ssq`=双色球，`3d`=福彩3D，`qlc`=七乐彩，`k8`=快乐8 | — | — |
| `issueCount=N` | 返回最近 N 期，**N 上限 2078** | **降序**（最新在前） | `0` |
| `issueStart` + `issueEnd` | 按期号区间，如 `2026001`~`2026120` | **升序**（最旧在前）⚠️ | `1` |
| `dayStart` + `dayEnd` | 按日期区间 `yyyy-MM-dd` | **升序** ⚠️ | `2` |
| `pageNo` + `pageSize` | **完全被忽略** | 降序 | `0` |

**三个实测出来的坑**：

1. **`pageNo`/`pageSize` 是摆设。** 传 `pageNo=1&pageSize=5` 和 `pageNo=2&pageSize=5` 返回**完全相同的 1773867 字节 / 2078 期**。福彩这个接口**不支持分页**，只有「最近 N 期」和「区间查询」两种模式。
2. **排序方向随参数变化。** `issueCount` 降序，`issueStart/issueEnd` 和 `dayStart/dayEnd` 是**升序**。用 `Tflag` 判断当前是哪种模式（0/1/2），别硬编码 `result[0]` 就是最新一期。
3. **`issueCount` 优先级高于 `pageNo`/`pageSize`。** `pageNo=1&pageSize=5&issueCount=20` → 返回 20 期。

#### `issueCount` 上限实测

| 传入 | 实际返回 | 最旧期号 | 体积 | 耗时 |
|---|---|---|---|---|
| 30 | 30 期 | 2026091 | 25 KB | — |
| 100 | 100 期 | 2026021 | 87 KB | — |
| 500 | 500 期 | 2023074 | 435 KB | — |
| 1000 | 1000 期 | 2020008 | 869 KB | 0.58 s |
| 2000 | 2000 期 | 2013079 | 1.71 MB | 0.87 s |
| 2077 | 2077 期 | 2013002 | 1772802 B | — |
| **2078** | **2078 期** | **2013001** | **1773867 B** | **0.85 s** |
| 2079 | 2078 期（封顶） | 2013001 | 1773867 B | — |
| 3600 / 5000 | 2078 期（封顶） | 2013001 | 1773867 B | 0.63~0.85 s |

> ⚠️ **福彩官网只存最近 2078 期（2013-001 至今）。** 2003~2012 年共 1439 期在官网**取不到**，只能靠 GitHub 镜像或 500.com。
> 对「核对最近中奖」这个核心场景，2078 期绰绰有余；只有做长周期走势分析才需要镜像补历史。

**解析注意（全部实测确认）**：

- 所有数字字段都是**字符串**，包括 `typenum` / `typemoney` / `sales` / `poolmoney`。用 `Int(...)` / `Double(...)` 显式转，别指望 `JSONDecoder` 自动推成数字。
- `red` 是**逗号分隔字符串**（不是数组），`blue` 是单个字符串。
- `date` 带 `(二)` 星期后缀，**必须截前 10 位**再解析，否则 `DateFormatter("yyyy-MM-dd")` 直接失败。也可以直接用 `week` 字段。
- `code` 是 **7 位**期号 `2026120`。
- `prizegrades` 恒有 **7 项**（`type` 1~7），但 **`type: 7` 在 30 期样本里全部为空字符串**，属预留位。解析时要跳过 `typenum == ""` 的项。
- 以下字段在 30 期样本中**全部为空**，是历史遗留，可以直接忽略：`blue2`、`addmoney`、`addmoney2`、`z2add`、`m2add`、`fyjCount`、`fyjMoney`、`specialRuleInfo`、`prizeSpecialInfo`、`compLimitInfo`、`msg`。
- `content` 是一等奖地域分布的**中文描述串**（`"内蒙古7注，上海1注，安徽1注，共9注。"`），不是结构化数据，想做「中奖地图」得自己正则解析。
- `detailsLink` / `videoLink` 是**相对路径**，要拼 `https://www.cwl.gov.cn` 前缀。

### 3.2 体彩官网 API（大乐透）✅ 实测通过

```
GET https://webapi.sporttery.cn/gateway/lottery/getHistoryPageListV1.qry?gameNo=85&provinceId=0&pageSize=100&isVerify=1&pageNo=1
```

#### ⚠️ WAF 精确规则（3 轮复测，100% 可复现）

**唯一的封禁条件：`User-Agent` 含 `Mozilla` 且不带 `Referer` → HTTP 567 + 腾讯 EdgeOne HTML 拦截页。**

| User-Agent | Referer | 结果 |
|---|---|---|
| （不发任何头） | — | ✅ 200 |
| `LotteryAssistant/1.0 CFNetwork/1560.4.6 Darwin/24.0.0`（**iOS 默认 UA**） | — | ✅ **200** |
| 同上 | `https://static.sporttery.cn/` | ✅ 200 |
| `Mozilla/5.0` | — | ❌ **567** |
| 完整 Chrome UA | — | ❌ **567** |
| 完整 Chrome UA | `https://static.sporttery.cn/` | ✅ 200 |
| `curl/8.7.1` | — | ✅ 200 |
| 空字符串 | — | ✅ 200 |

**这条规则反直觉但很有用**：

- ✅ **iOS `URLSession` 默认 UA 是 `AppName/version CFNetwork/xxx Darwin/xxx`，不含 `Mozilla`，所以开箱即用，什么都不用设。**
- ❌ 反倒是「好心」去模仿浏览器 UA 会**触发封禁** —— v1 版文档和上游 `ahbencat/futurefortune` 的脚本都是这么写的，所以在 GitHub Actions（境外 IP）上才会撞上 567，被误判成「地域封锁」。
- 🛡️ **稳妥做法：显式带上 `Referer: https://static.sporttery.cn/`。** 这样无论 UA 是什么都返回 200，不依赖「UA 恰好不含 Mozilla」这个脆弱前提。
- 567 响应体是 HTML（腾讯 EdgeOne 拦截页，`<!doctype html>...<title></title>`，约 7.3 KB），**不是 JSON**，解析会失败。要按 status code 提前拦截并给出可读错误。

> v1 版文档写的「境外 IP 返回 567」这个说法**不准确**：真正的触发条件是 UA + Referer 组合。上游仓库的脚本用了完整 Chrome UA 但没配 Referer，所以才被封，然后误归因为 IP 问题、绕道去抓江苏体彩网。

#### 其他实测特性

- 落地 IP `43.242.199.237`，`Server: TencentEdgeOne`
- **CORS 完全开放**：`access-control-allow-origin: *`、`access-control-allow-methods: GET, POST, OPTIONS`、`access-control-allow-credentials: true` → 浏览器/H5 也能直接调
- 延迟 **83~356 ms**
- **`pageSize` 硬上限 100**：传 200/500/1000/3000 全部截断为 100（响应体积都是 305396 B）
- 分页正常工作：`total=2938`、`pageSize=100` → `pages=30`
- **全量抓取实测**：`pageNo` 1→30 循环，间隔 0.25 s，**23.2 秒拿到全部 2938 期**，与镜像逐期比对 **0 处不一致**

#### 请求参数

| 参数 | 说明 |
|---|---|
| `gameNo` | `85`=超级大乐透，`35`=排列三，`350133`=排列五，`04`=7 星彩 |
| `provinceId` | `0`=全国 |
| `pageSize` | 每页条数，**上限 100** |
| `pageNo` | 页码，从 1 开始，**最大 = ceil(total/pageSize)** |
| `isVerify` | 固定 `1` |

| **3+0** | 六等奖 | **七等奖** | ❌ |
| **2+1** | 六等奖 | **七等奖** | ❌ |
| **1+2** | 六等奖 | **七等奖** | ❌ |
| **0+2** | 六等奖 | **七等奖** | ❌ |

修正后应为：

```
一等奖   5+2
二等奖   5+1
三等奖   5+0 或 4+2
四等奖   4+1
五等奖   4+0 或 3+2
六等奖   3+1 或 2+2
七等奖   3+0 或 2+1 或 1+2 或 0+2
不中奖   其余
```

另外三个相关问题：

1. **缺「七等奖」** —— App 的 `switch` 里没有这个分支，中七等奖的用户会被判成六等奖（奖金 5 元 vs 实际 7 元，且提示文案错误）。
2. **`isAdditional` 字段从未被使用** —— `LotteryTicket` 有 `isAdditional`、`purchaseCost` 也按 3 元算了，但 `PrizeChecker` 完全没读它。官方一二等奖各有独立的「追加」奖级（`group` 201 / 401），追加投注的一等奖能多拿 80%。
3. **`estimatedPrize` 恒为 0** —— `PrizeChecker.apply()` 里写死 `ticket.estimatedPrize = 0`。现在官网直接给 `stakeAmountFormat`，固定奖级（三~七等）可以算出准确金额，浮动奖级可以给当期实际单注奖金。

> **架构建议**：奖级规则**不要硬编码在 `switch` 里**。规则会变（大乐透历史上就从 9 级改成了现在的 7 级），固定奖金也会因派奖活动浮动。
> 更好的做法是把「中奖条件 → 奖级」做成数据驱动的配置表，奖金直接取官网当期 `stakeAmountFormat`。这样规则一变，只改数据不改逻辑。

## 5. 四个必须注意的坑

### 坑 1：期号格式不统一 ⚠️ 最容易踩

同一个「2026 年第 120 期双色球」，各源写法**实测**如下：

| 来源 | 双色球期号 | 大乐透期号 |
|---|---|---|
| 福彩官网 `code` | **`2026120`（7 位）** | — |
| 体彩官网 `lotteryDrawNum` | — | **`26120`（5 位）** |
| 500.com | `26120`（5 位） | `26120`（5 位） |
| `ahbencat/futurefortune` | `2026120`（7 位） | `26120`（5 位） |
| `yangxb919/lottery-data` | `26120`（5 位） | `26120`（5 位） |
| `devpenn/lottery-data` | `26120`（5 位） | `26120`（5 位） |

**归一化规则**：

```
双色球规范 = 7 位 YYYYNNN。收到 5 位则补 "20" 前缀。
大乐透规范 = 5 位 YYNNN。  收到 7 位则去掉前 2 位。
例外：大乐透 2007 年早期期号本身就是 07001 这种 5 位，不要动。
```

不做归一化的后果：`LotteryDraw.recordID`（当前是 `"\(kind.rawValue)-\(issueNumber)"`）会把同一次开奖存成两条，且 `LotteryTicket.issueNumber` 与 `LotteryDraw.issueNumber` 匹配不上 → **永远判不出中奖**。

### 坑 2：体彩 WAF 的「伪装浏览器反被封」

见 [§3.2](#32-体彩官网-api大乐透-实测通过)。**带 `Mozilla` UA 又不带 Referer 才会 567**。
→ 稳妥做法：**显式带 `Referer: https://static.sporttery.cn/`**，UA 随便。

### 坑 3：时区与开奖时刻

- 所有源的日期字段都是**北京时间（Asia/Shanghai）的日期**，无时间部分
- 解析必须固定 `TimeZone(identifier: "Asia/Shanghai")` + `Locale(identifier: "en_US_POSIX")`，否则设备在其他时区/历法时会偏移一天
- 福彩 `date` 是 `"2026-10-20(二)"`，**要截前 10 位**
- 体彩 `lotteryDrawTime` 是干净的 `"2026-10-21"`，但 `lotteryPaidBeginTime`/`lotteryPaidEndTime` 是 `"2026-10-21 23:30:01"`（空格分隔，非 ISO8601），要单独的 formatter
- 数据落库延迟（实测推断）：
  - 体彩官网：26120 期（10-21 20:30 开奖）的 `lotteryPaidBeginTime` 是 **`2026-10-21 23:30:01`** → 官网数据约 **23:30 后**完整
  - 开源镜像：`ahbencat` 次日 04:00、`devpenn` 当日 22:30、`yangxb919` 约次日 02:30（`pushed_at: 2026-10-21T18:32:56Z`）+ jsDelivr 缓存最多 12 h
- 结论：**别承诺「开奖即时更新」**。同步时机放在开奖日 **23:30 之后**或次日早上，才不会出现「明明开奖了 App 还没数据」。

### 坑 4：官网响应里所有数字都是字符串

福彩的 `sales`/`poolmoney`/`typenum`/`typemoney`、体彩的 `stakeCount`/`poolBalanceAfterdraw`/`totalSaleAmount`/`stakeAmount` **全部是字符串**，且体彩的还**带千分位逗号和小数**。

```
"825,893,883.63"  → 去逗号 → "825893883.63" → Double
"1035363275"      → 直接 Int/Double
""                → 福彩 type:7 恒为空串，Int("") = nil，要跳过而不是崩
```
体彩提供了 `stakeAmountFormat`（纯数字字符串）专门省掉这一步，**优先用它**。

## 6. 接入方案对比（实测后重新推荐）

### 方案 A：iOS 直连官网 API ⭐⭐⭐ 现在的首选

```
iOS App ──HTTPS──> cwl.gov.cn    (双色球，1 次请求 2078 期)
        └─HTTPS──> sporttery.cn  (大乐透，30 次请求 2938 期)
```

- **工作量**：1 天
- **成本**：0
- **优点**：**实测 55~356 ms**，比镜像快 50~300 倍；字段最全（奖池、6/9 档奖级、销量、兑奖起止时间、官方公告 PDF、出球原序）；数据权威；无 ATS 问题（都是 HTTPS）；体彩还开了 `Access-Control-Allow-Origin: *`
- **缺点**：
  - 双色球**只能拿最近 2078 期**，2003~2012 的 1439 期取不到
  - 体彩全量要翻 30 页（23 秒，可做增量只翻第 1 页）
  - 属非公开契约，字段/地址可能变（但两家都是长期稳定运行的官网接口）
  - 体彩有一条 WAF 规则，需带 Referer 兜底
- **适用**：**你现在这个项目最该走的路**

### 方案 B：官网直连 + 镜像补历史/兜底 ⭐⭐⭐ 完整方案

```
主链路：官网 API（快、全字段）
补历史：GitHub 镜像（只有它能给 2003~2012 的双色球）
兜底：  镜像 / 500.com（官网挂了或改版时降级）
```

- 在 `LotteryDataProviding` 下多实现两个 provider，用责任链依次尝试
- 历史数据只需**首次安装时拉一次**，之后走增量

### 方案 C：自建 GitHub Actions + CDN ⭐ 现在不推荐了

v1 版推荐这个，理由是「官网反爬 + 境外 IP 封锁」。**实测证明这个前提不成立**：官网开放、快速、字段全，而 GitHub CDN 在国内慢到 2~25 秒。

只有在这些情况下才值得自建：
- 需要**服务端**统一收口（多端共用、隐藏商业 API Key）
- 需要**预处理**（把 5 个源合并、算好走势指标再下发）
- App Store 审核对「直连政府网站」有顾虑

### 方案 D：iOS 直连 500.com ❌ 不推荐

HTML 解析放进 App 太重，且期号格式、字段都不如官网。只在服务端方案里作为补充源。

## 7. iOS 端落地要点

### 7.1 ATS

- 福彩、体彩、jsDelivr、raw.githubusercontent **全部是 HTTPS**，`GENERATE_INFOPLIST_FILE = YES` 默认配置即可，**不需要** `NSAllowsArbitraryLoads`
- 福彩 `http://` 会 302 到 `https://`，直接用 https 版本
- 唯一例外：若要用 `drawPdfUrl`（`https://pdf.sporttery.cn`，已实测 200）也是 HTTPS，无问题

### 7.2 请求头设置（关键）

```
体彩：必须设 Referer: https://static.sporttery.cn/
      UA 保持 URLSession 默认（CFNetwork/...，不含 Mozilla）→ 200
      ⚠️ 千万不要「好心」把 UA 改成浏览器 UA，除非同时也设了 Referer
福彩：什么都不用设，裸请求即 200
镜像：建议设 Accept: application/json
```

### 7.3 超时与缓存

| 源 | 建议 request 超时 | 建议 resource 超时 | 缓存 |
|---|---|---|---|
| 福彩官网 | 15 s | 60 s | ❌ 无效（响应头 `no-store`），需自己在本地做「距上次同步 < N 小时则跳过」 |
| 体彩官网 | 15 s | 90 s（全量翻页） | 同上 |
| GitHub 镜像 | **30 s** | **120 s**（实测会到 25 s） | ✅ 可配 `URLCache`，但要容忍最多 12 h 的 jsDelivr 缓存 |

- 福彩 `Cache-Control: no-cache, no-store, max-age=0, must-revalidate` → **`URLCache` 对福彩完全无效**，别指望它省流量。2078 期 = 1.77 MB，每次全量拉。建议本地存 `lastSyncAt`，间隔小于 6 h 直接跳过。
- 并发去重：同一彩种的重复刷新复用同一个 `Task`。当前 `DrawListView` 已用 `.disabled(isSynchronizing)` 挡住了，够用。

### 7.4 落库（SwiftData）

- **去重键**：`LotteryDraw.recordID`（`@Attribute(.unique)`），但 `issueNumber` 必须先按 [§5 坑1](#坑-1期号格式不统一--最容易踩) 归一化
- **增量 upsert**：把已有 `recordID` 一次读成 `Set<String>`，只 `insert` 缺失的。**不要**在循环里 `existing.contains(where:)`（O(n²)，见 §11.4）
- **不要覆盖已有记录**，否则会抹掉已存的奖池/奖级
- **入库前校验**：号码个数、区间、同区不重复、日期可解析 → 不满足就跳过该行，别 throw 中断整批
- **排序**：`DrawListView` 已按 `drawDate` 倒序，正确。**不要**按 `issueNumber` 字符串排序（大乐透 `07001` 与 `26120` 混排会乱）

### 7.5 首次启动策略

当前 `LotteryAssistantApp.init()` 同步调用 `AppDataSeeder.seedIfNeeded`。建议：

1. **删掉假数据**（见 §11.4 第 1、2 条，`2026120` 与真实数据主键直接冲突）
2. 首屏改成 loading 骨架屏或「点击同步」引导页
3. `ContentView.task {}` 里异步拉官网
4. 失败时显示非阻塞提示条，不要 `fatalError`

## 11. 结合本项目现有代码的对接指引

### 11.1 现有数据链路

```
SettingsView        用户填「授权 API 地址」+「API Key」
      │             → ProviderConfiguration.endpoint   (UserDefaults)
      │             → ProviderConfiguration.saveAPIKey (Keychain, kSecClassGenericPassword)
      ▼
DrawListView        toolbar 刷新按钮 → synchronize()   （已用 .disabled(isSynchronizing) 防重入）
      ▼
DrawSyncService     @MainActor, synchronize(context:)
      │             1. provider.fetchLatestDraws()
      │             2. 校验号码规则 isValid(payload:for:)
      │             3. 按 recordID 去重后 insert
      ▼
ConfiguredLotteryDataProvider
                    GET <endpoint>
                    Authorization: Bearer <apiKey>
                    Accept: application/json
                    → JSONDecoder(dateDecodingStrategy: .iso8601)
                    → [LotteryDrawPayload]
      ▼
SwiftData           LotteryDraw
```

**现有架构要求「一个带 Bearer 鉴权的自定义 HTTPS JSON 接口」**，但本次实测证明官网根本不需要鉴权、还更快更全。所以建议**新增一个直连官网的 provider**，`ConfiguredLotteryDataProvider` 保留给「自己有后端」的场景。

因为已经抽象出了 `LotteryDataProviding` 协议，加 provider **不用改 `DrawSyncService` 和任何 UI**。

### 11.2 若继续用自定义后端，它必须返回的 JSON 契约

由 `LotteryDrawPayload` 反推，接口必须返回**顶层数组**：

```json
[
  { "lottery": "doubleColorBall", "issueNumber": "2026120",
    "drawDate": "2026-10-20T00:00:00Z",
    "frontNumbers": [13, 14, 16, 18, 20, 31], "backNumbers": [3],
    "poolAmount": 1035363275 },
  { "lottery": "superLotto", "issueNumber": "26120",
    "drawDate": "2026-10-21T00:00:00Z",
    "frontNumbers": [1, 6, 10, 15, 32], "backNumbers": [3, 4],
    "poolAmount": 825893883.63 }
]
```

四个硬性约束，违反任一条整个同步就失败：

| 字段 | 约束 | 违反后果 |
|---|---|---|
| `lottery` | 必须是 `LotteryKind.rawValue`，即 **`doubleColorBall`** / **`superLotto`**（不是 `ssq`/`dlt`） | `throw invalidDrawData` |
| `drawDate` | 必须是**完整 ISO8601**，如 `2026-10-20T00:00:00Z` | `.iso8601` 解不了纯日期 `"2026-10-20"`，抛 `invalidResponse` |
| `frontNumbers`/`backNumbers` | **整数数组**，个数与区间必须匹配彩种规则 | `throw invalidDrawData`，且**已 insert 的数据不会 save** |
| 顶层 | 必须是**数组**，不能包在 `{"data": [...]}` 里 | `throw invalidResponse` |

### 11.3 接真实数据前建议修的 11 个问题

按严重程度排序，前 4 条会直接导致功能错误：

| # | 位置 | 问题 | 严重度 |
|---|---|---|---|
| 1 | `AppDataSeeder.swift` | 假数据双色球期号 `2026120` 与**真实 2026120 期的 `recordID` 完全冲突**（`doubleColorBall-2026120`）。因 `recordID` 标了 `@Attribute(.unique)`，真实数据插不进去，用户永远看到假号码 `03 07 12 18 24 31 + 09`（**真实是 `13 14 16 18 20 31 + 03`**，已用福彩官网核实） | 🔴 致命 |
| 2 | `AppDataSeeder.swift` | 假数据大乐透期号 `2026132`/`2026131`/`2026130` 是 **7 位**，真实格式是 5 位（`26132`）。`recordID` 不冲突但会多出**三期根本不存在的开奖记录**，且它们的 `drawDate` 是最近几天 → 会抢占 `DrawListView` 顶部、干扰「最新一期」判断和 `PrizeChecker` 匹配 | 🔴 致命 |
| 3 | `Domain/PrizeChecker.swift` | **大乐透奖级映射 7 处错误**，且缺「七等奖」。详见 [§4.3](#43-你的-prizecheckerswift-需要改什么) | 🔴 致命 |
| 4 | `ConfiguredLotteryDataProvider` | `.iso8601` 与上游纯日期 `date` 不兼容（见 §11.2） | 🔴 致命 |
| 5 | `DrawSyncService.synchronize` | 一条脏数据 `throw invalidDrawData` → **整批中断**，且 `context.save()` 在末尾，前面 insert 的全部丢弃。应改为 skip + 计数 + 汇总告警 | 🟠 高 |
| 6 | `DrawSyncService.synchronize` | `existing.contains(where:)` 在循环内 → **O(n²)**。全量 6455 期约 2×10⁷ 次比较，且跑在 `@MainActor` 上会明显卡 UI。应先构建 `Set<String>` | 🟠 高 |
| 7 | `DrawSyncService.synchronize` | `recordID` 直接用 `payload.issueNumber` 拼接，**没做期号归一化**（§5 坑1） | 🟠 高 |
| 8 | `Domain/PrizeChecker.swift` | `isAdditional` 从未被读取（官方一二等奖各有独立追加奖级）；`estimatedPrize` 写死为 0（官网有 `stakeAmountFormat` / `typemoney` 可用） | 🟠 高 |
| 9 | `ConfiguredLotteryDataProvider` | 函数体内嵌了一个 `MockLotteryDataProvider` struct，**定义了但从未使用**（死代码），位置还在 URL 校验之前，极易误读；其 `issueNumber: "MOCK-001"` 一旦被误接会污染数据库 | 🟡 中 |
| 10 | `ProviderConfiguration.endpoint` | 未校验 scheme。用户填 `http://` 时被 ATS 静默拦截，最终报的是 `invalidResponse`（“数据格式无法识别”），**错误信息完全误导排查方向** | 🟡 中 |
| 11 | `DrawSyncService` | `@MainActor` 上做 JSON 解码 + 批量插入。建议解码放后台，只把写库放主线程；或改用 `ModelActor` + 后台 `ModelContext` | 🟢 低 |

> 第 1、2 条处理建议：**接入真实数据的同时删掉 `AppDataSeeder` 的假数据**，首屏改 loading 骨架屏或「点击同步」引导页。若为演示必须保留，把假期号改成不可能冲突的格式（如 `DEMO-0001`）。

## 12. 合规提示

1. 开奖数据本身属公开信息，但**抓取行为受目标网站服务条款约束**。请：
   - 控制频率（建议 ≤ 1 次/小时；体彩全量翻页时加 0.25 s 间隔，实测 30 页无异常）
   - 遵守 `robots.txt`
   - 不做商用转售
   - 福彩响应头是 `no-store`，别硬缓存绕过
2. 使用第三方开源仓库数据，遵守其 LICENSE（已核实）：
   - `ahbencat/futurefortune` → **MIT**，需在「关于」页保留版权声明与许可全文
   - `yangxb919/lottery-data` → **无 LICENSE**
   - `devpenn/lottery-data` → **无 LICENSE**

   > ⚠️ 无 LICENSE 的仓库法律上默认「保留所有权利」，严格来说不能分发其数据/代码。自用学习无妨，若要上架 App Store，建议只用 MIT 那个，或干脆直连官网（数据来自政府公开信息，无授权障碍）。
3. 本 App 若仅做「号码记录 + 中奖核对」属工具类，合规风险低；但**不要**加入代购、投注、返奖等资金相关功能。也没有任何算法能提高中奖概率（实测总中奖率就是 **1/15**，一等奖概率 **1/21,425,712**），UI 文案需避免误导 —— `DrawDetailView` 底部「以官方当期规则为准」的提示建议保留并加强。
